## Benchmarks

`weiqi.tools.benchmark` on `testdata/sgf/maruyama-ito-1976.sgf` (235 moves,
236 analysed positions, Japanese rules, komi 5.5, no ownership):

```bash
cd python
KATAGO_MODEL_PATH=/opt/homebrew/share/katago/kata1-b18c384nbt-s9996604416-d4316597426.bin.gz \
  uv run python -m weiqi.tools.benchmark ../testdata/sgf/maruyama-ito-1976.sgf \
  --visits 32 200 --repeats 2 --output report.json
```

Each scenario runs in a fresh worker process. **Cold** starts the clock
before launching KataGo; **warm** times the game after KataGo has started and
answered a warm-up query on a position that is not in the game. The warm
worker then times a second analysis answered entirely from a new SQLite
cache. Peak RSS is the KataGo process's maximum resident set size from
`getrusage(RUSAGE_CHILDREN)`; memory that Metal allocates on the GPU side
may not be included.

KataGo 1.18.2, 2026-11-08 (two repeats per cell):

| Visits | Cold: start-up | Cold: whole game incl. start-up | Warm: whole game | Warm: cached re-read | KataGo peak RSS |
| --- | --- | --- | --- | --- | --- |
| 32 | 0.72 s, 0.93 s | 71.7 s, 79.0 s | 73.8 s, 85.6 s | 0.04 s, 0.02 s | 833–943 MiB |
| 200 | 0.71 s, 1.10 s | 432.1 s, 475.4 s | 428.7 s, 412.1 s | 0.03 s, 0.05 s | 833–942 MiB |

KataGo 1.16.4, the same day, about an hour earlier:

| Visits | Cold: start-up | Cold: whole game incl. start-up | Warm: whole game | Warm: cached re-read | KataGo peak RSS |
| --- | --- | --- | --- | --- | --- |
| 32 | 0.78 s, 0.63 s | 59.3 s, 60.8 s | 57.5 s, 64.0 s | 0.02 s, 0.01 s | 707–830 MiB |
| 200 | 0.65 s, 0.66 s | 395.7 s, 370.2 s | 401.7 s, 380.8 s | 0.02 s, 0.02 s | 828–831 MiB |

What the numbers show, and what they do not:

- Starting KataGo, loading the model and checking readiness take under
  1.2 s, so cold and warm runs differ by less than the spread between
  repeats.
- A whole game read back from the cache takes 0.01–0.05 s.
- **The two versions are not different in speed on this evidence.** The
  1.18.2 runs above were slower than the earlier 1.16.4 runs, so the two
  versions were then run alternately at 32 visits (1.16.4, 1.18.2, 1.16.4,
  1.18.2; cold then warm each): 1.16.4 took 81.1, 77.1, 73.4 and 74.0 s,
  1.18.2 took 74.7, 73.2, 73.5 and 73.7 s. The same 1.16.4 game took 57–64 s
  an hour earlier, so the state of the machine moves these times by
  25–35 %, more than any version difference measured here. The cause was
  not measured; heat after an hour of continuous load is one possibility.
- Times on this machine are therefore reproducible only to roughly ±20 %.
  Comparisons need runs made alternately in one session.
- The config has not been tuned (MIGRATION E11: benchmark before changing
  values).

## KataGo upgrade

The owner asked on 2026-11-08 to upgrade KataGo. `brew upgrade katago`
(with `HOMEBREW_NO_INSTALL_CLEANUP=1`) installed `1.18.2_2` from Homebrew's
bottle and added its new dependencies `abseil` 20260817.0 and `protobuf`
36.2; no other package changed. The 1.16.4 keg stays in the Cellar as a
fallback. Both versions report the Metal backend; 1.18.2 reports
"MPSGraph GPU-only mode" at start-up. The b18 model file is the same in both
(same SHA-256). After the upgrade, all Python tests and the 9 live tests
pass unchanged.

The recorded fixture (`testdata/engine/short-game.json`) stays a 1.16.4
recording, as its provenance says: replay tests check our code against what
KataGo really sent and do not depend on the installed version.

## Decisions

- ADR-P03 and ADR-P08 were accepted at the start of M3 and are built as
  described in ARCHITECTURE §5.3 and §10.3.
- SQLAlchemy runs synchronously; async repository methods use
  `asyncio.to_thread`, so no async database driver is needed.
- The engine layer defines the `ResultStore` interface and the storage layer
  implements it; the engine never imports the database.
- A cancelled or failed query stores nothing; results are stored when the
  query completes.
- KataGo 1.18.2 is the installed version from this milestone on.

## Known items

- `config/katago/analysis.cfg` contains `logToFile = false`, which KataGo
  (1.16.4 and 1.18.2) reports as an unused key at start-up. It is copied
  unchanged from the prototype; removing it would change the config hash and
  every `query_key`, so it waits for the config review (MIGRATION E11).
- Peak RSS may not include memory that Metal allocates for the GPU.
- The forced played-move search (MIGRATION E04) and score loss arrive in M4.
- Results of a cancelled game are not kept; the M4 job design may store
  turns as they arrive.
